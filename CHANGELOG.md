## [0.1.0] - 2026-10-12

First public release.

### Added

- The router: a SessionStart hook injects `hooks/flow.md`, which sorts every request into a lane (Trivial, Bug, Change, Feature, No repo) and reports any in-flight spec. After a compaction or resume, the agent rebuilds its state from disk (spec and ticket `Status:` lines, `git log`, `git status`) before acting.
- Twelve skills adapted from Matt Pocock's: `grill`, `domain`, `spec`, `tickets`, `build`, `tdd`, `review`, `pr`, `retro`, `prototype`, `debug`, `handoff`.
- Four human gates (G1 aligned, G2 test seams, G3 spec, G4 tickets), each asked as a structured question with the material in its preview. Without a question tool (headless `claude -p`, or a harness that lacks one), a gate prints its options as a numbered list, recommended first, and ends the turn; a one-way door (merge, delete, push) goes ahead only on a reply that names it.
- The merge guard: a PreToolUse hook (`hooks/merge-guard.sh`, plain sh) that refuses `git merge`, `git pull` of another branch, `git branch -d/-D`, `git push`, `gh pr create` and `gh pr merge` on a branch keel created until the branch's ledger shows a review and a disposition for every finding, unless the user waived review in their own words. The ledger is one file per keel-created branch under the git common dir (`.git/keel/<branch>`), shared by every worktree and never committed; its formats live in `skills/review/LEDGER.md`. Other branches, other commands and unparseable input pass. See `docs/adr/0001-merge-guard-hook.md`.
- `keel:build`: a fresh implementer subagent per ticket, parallel tickets in worktrees with merger subagents, a two-axis review, a fixer, retro, and a finish choice (merge locally, open a PR, or leave the branch). Resumes from the spec, tickets and branches after a crash or `/clear`. Implementers and the fixer quote the spec's hard constraints word for word and never edit tests to reach green; a merger that can't turn the suite green undoes its merge. Every review finding ends fixed (the reviewer's fix as written, or why not), refuted with evidence, or escalated to the user, and is written to the ledger. A finished spec says it is a historical record.
- `keel:review`: Standards and Spec axes as parallel sub-agents, each reading its brief (`STANDARDS.md`, `SPEC.md`) by path so the orchestrator can't paraphrase it. It reports only proven defects: a finding is a defect in the changed behaviour shown by a probe the reviewer ran (command and output) or a quoted line, and zero findings is valid. Speculative or unproven minor concerns are listed under `## Residual risks` with no id, no ledger line and no disposition. The Spec axis aims its break attempts (uncommitted scratch scripts) at the boundary decision or the spec's rules and their violation cases, checks every decision against the cases the work covers, names any existing guard covering the same behaviour and whether the change is looser or stricter, flags weakened tests, and lists what it tried when it finds nothing. Claude Code's bundled `/code-review` runs only when the user asks for it. Findings are numbered `S`/`P`/`C` and recorded in the ledger. A finding is refuted as "pre-existing", "equally loose elsewhere" or "out of scope" only by a run showing the same input behaves identically at the fixed point; an escalation recommends the fix, and the regression test gains the finding's failing input.
- `keel:debug`: a tight red loop first, then a boundary decision before the fix. Debug reads the code around the bug and every existing parser, validator, guard or invariant for the same thing (found by concept, not by the bug's idiom), then asks one question, printed as a fixed block with lettered, costed options before any edit to source: the rule the fix enforces (a rule or grammar, never examples), the cases it accepts and rejects, and the existing rule it adopts by file:line. It recommends the strictest option the repo's own rules or the input's spec support; without a question tool, it prints the block and the recommendation stands. The accepted and rejected cases are the near-misses, and the regression test covers them. A looser rule elsewhere is a follow-up for the retro and never loosens the fix. A fix lands on `fix/<slug>` after lint, typecheck and the full suite, then goes through `keel:review`, whose spec is the decision, the bug report and the confirmed hypothesis, before the retro and the merge question.
- `keel:grill`: rounds over the design tree; each question holds one decision, its options are lettered and each carries its cost, and the recommendation handles every case the work covers.
- `keel:tdd`: tests only at agreed seams, each with a note on what it catches and misses; existing tests that start tripping are treated as probes before anyone edits them.
- `keel:retro`: improves the environment (checks, standards, pointers) only on a real pick; product code, tests and dependency pins are listed as follow-ups. After a fix (the Bug lane and an inline build) it lists its candidates and stops, and applies one only when a reply that arrives after the listing names it.
- The context note: a hook reads the session's size from the transcript and, at 100k and 140k tokens, tells the agent to offer `keel:handoff` at the next boundary. `keel:handoff` ends with a paste-ready prompt for the next session. G4 asks where the build should run.
- Adapters: a Codex plugin manifest and router hook, an OpenCode plugin (1.x and 2.x), and an installer for any harness that reads `.agents/skills`.
- Lean instruction load: process detail lives in references read only at the step that needs them (spec-mode build in `skills/build/SPEC-MODE.md`, test examples, anti-patterns and design vocabulary in `skills/tdd/tests.md`, loop building and instrumenting in `skills/debug/LOOPS.md`, retro's writing rules in `skills/retro/WRITING.md`, the bundled code review in `skills/review/CODE-REVIEW.md`). The files the Bug path always loads come to about 3.4k words and the Change path's about 4.0k, 60% of before.
- Tests: hook tests for the router, the context note and the merge guard; `scripts/lint.sh` (skill limits, strict YAML frontmatter, references, no em-dashes in tracked prose, and a word budget over the files each path always loads: 3.5k for Bug, 4.0k for Change); `scripts/test-graders.sh` (each eval regex grader against pass and fail fixtures, no API spend); a `claude plugin eval` suite with seven trigger-correctness cases and nine regression cases that resume recorded sessions (`evals/`), three of them for the boundary decision, the pre-existing refutation rule and the retro after a blanket reply.
- One step for a branch and its ledger: `skills/review/new-branch.sh` (plain sh) creates and switches to the branch and appends `created <short sha of the start point>` to its ledger, from any worktree, and refuses a branch that exists. keel:debug and keel:build create their `fix/` and `feat/` branches only through it, so the merge guard sees every one; ticket branches still get no ledger. The Spec reviewer searches the repo itself, by the input's name rather than the decision's Adopts line or the bug's idiom, for every parser or validator of the same input, and an input such a rule rejects that the change accepts is a finding, not a residual risk. The boundary decision's Rejects cover each part its Rule names, empty and with a wrong character, and the block is always printed as plain text before the question or the fix. `scripts/test-new-branch.sh` tests the script and the guard end to end.
- Credits for the ideas adapted from compound-engineering, BMAD-METHOD, superpowers and spec-kit (NOTICE, README).

### Known gaps

- Codex: the plugin installs and the router hook is wired, but the end-to-end smoke test (lane, skill, gate) hasn't run yet.
- The merge guard is a Claude Code hook; in Codex and OpenCode the ledger is written but nothing refuses a merge.
- Tier 3 harnesses (Cursor, Gemini CLI, Copilot, Amp, Pi) are best effort and untested.
